Paper

Accelerator Choice Is Not Enough: AlphaFold2 Inference on Cloud TPUs. Lorenzo Pazienza, Ihab El Bani · arXiv preprint, September 2026 · cs.DC. Links: arXiv page, PDF, LaTeX source, code and data.

Abstract

AlphaFold2 is written in JAX, so the same inference code compiles and runs unchanged on CPUs, GPUs and Google Cloud TPUs. That portability makes the accelerator look like the main decision a user has to make. We show that it is not. Running one AlphaFold2 inference workload across a Colab CPU runtime, an NVIDIA T4 GPU and a dedicated eight-chip Cloud TPU v5e slice, we find a large hardware advantage for the TPU, 0.47 s per call in steady state on a single chip against 13.1 s on the T4 in the same measurement campaign, and three ways in which the software layer decides how much of it a user actually gets. The default execution path uses one chip of the eight, and at list prices the idle capacity makes the slice cost about as much per prediction as the GPU. Batching with JAX’s vmap never exceeds single-query throughput, while mapping queries across chips with JAX’s pmap gives eight chips 6.5-7.9x the throughput of one on a matched grid; automatic sharding leaves the per-chip footprint unchanged, consistent with replication, most plausibly because AlphaFold2 carries no sharding annotations. Our retained trace analysis of a first call at a new input shape reports about three quarters of the traced span in JAX tracing and compilation rather than execution. Reruns five weeks later reproduced neither cloud baseline, the GPU one off by roughly a factor of two, so the hardware ratio above is specific to one campaign.

Problem

What decides the performance a user actually gets? Biology needs a protein’s 3D shape. AlphaFold 2 (DeepMind) made high-accuracy structure prediction practical with a large JAX/Haiku Evoformer, but running that inference is expensive and opaque across accelerators: cold XLA compiles, underused TPU pods, unclear CPU vs GPU vs TPU trade-offs. What we did: we ran AlphaFold2’s JAX forward pass on a Google Colab CPU runtime (Intel Xeon, 2 vCPU), a Google Colab NVIDIA Tesla T4 and a Stanford GKE TPU v5e-8 slice (tpu-v5-lite-podslice, 2×4, 8 chips). Single-query timings use the same 118-residue input, AlphaFold 2 model_3, 0 recycles and randomly initialized parameters on every backend. Then we asked where the time goes on a first call, and what it takes to put all eight chips to work. Follow-up: AlphaFold 3 (a separate diffusion codebase) on the same Google Colab Intel Xeon CPU and NVIDIA Tesla T4, plus a confirmed finding that its public release does not support TPU - see #af3.

Approach

One script spike_tpu_forward_pass.py → Google Colab Intel Xeon CPU (result_cpu-colab.json), Google Colab NVIDIA Tesla T4 (result_gpu-t4.json), Stanford GKE TPU v5e-8 / tpu-v5-lite-podslice 2×4 (result_tpu + traces). Docker for the CPU/GPU images; Kubernetes Job + Kueue on GKE for the TPU worker. Systems timings: AlphaFold 2 model_3, 0 recycles, 118-residue input, Haiku random init rather than trained weights, so the same compiled graph is exercised on every backend. The multi-chip and scaling-grid experiments use a different synthetic input family, so their numbers are compared among themselves, not with the single-query baseline. The ubiquitin structure lower down the page is separate: ESMFold with trained weights, for biology, not for the clocks.

Results - Steady-state predict latency

Callout: 0.47s. model_3, 0 recycles, 118 residues. Log-scaled bars. Single-chip comparison, August 2026 campaign.

Backend Time vs CPU
CPU Xeon (Google Colab, 2 vCPU) 212.1s 1×
GPU Tesla T4 (Google Colab) 13.1s 16.2×
TPU v5e-8 (Stanford GKE, 2×4) 0.47s 451×

The TPU figure is one chip of the eight in the slice.

Did the baselines reproduce?

No. Reruns five weeks later, with the same input and metrics, found the CPU 1.64-1.69× slower (three September sessions) and the T4 about 2× faster (6.567 s, one September session), for reasons the records cannot identify. The TPU-over-GPU ratio above is therefore specific to the August campaign.

First predict / steady-state

As timed: CPU 1.28× · GPU 7.46× · TPU 59.1×. The CPU and GPU first calls ran with the profiler inside the timer; removing that overhead gives about 1.11× and about 4.25×. The TPU figure is not correctable, because no TPU run log survives. In a retained trace of one TPU first call, about 76% of the traced apply_fn span is self time in JAX’s tracing and compilation path rather than device execution.

Experiments - Twelve TPU follow-ups

Amber rail = negative result. Click + for method notes on the live UI.

Scaling

  1. Sequence length - 14.6× time for 8.3× length. Super-linear; swept 60–500 residues.
  2. Recycle depth - ~0.46s per extra recycle; compile flat after first.
  3. Chip visibility - 1 of 8 chips used on default path.

Bottleneck & fix

  1. Profiler trace - 76% of the traced apply_fn span (16.56s) in pjit cache_miss (host JIT), not of the whole first call (27.78s). Reported from our trace analysis; the raw trace is not in the repository.
  2. Compilation cache - 6.81× faster init_params (66.48s → 20.72s) across a process restart; first predict 1.90× faster with a warm cache; steady-state unchanged.
  3. Precision bf16 - −40% steady-state HBM; little runtime change.

Multi-chip

  1. Multi-query batching - lower proteins/sec vs batch=1 (negative). At batch 1, 2, 4 and 8, measured throughput was 2.051, 1.928, 1.487 and 1.508 proteins/sec, that is 0.94×, 0.73× and 0.74× the batch-1 rate; the decline is not monotonic, so the values are reported as measured. vmap stayed on one chip.
  1. pmap - 6.92× throughput over the single-query baseline (2.13 → 14.72 proteins/sec on 8 chips, 86.5% parallel efficiency). On the matched chip-count grid, eight chips give 6.53× the throughput of one at 100 residues (81.6% efficiency) and 7.91× at 1000 (98.9%).
  2. Auto-sharding (auto-mesh) - 463 MB per chip, unchanged (negative); consistent with replication. Best explanation: no sharding annotations for the partitioner to propagate from, stated as a hypothesis. Which partitioner actually ran is not recorded.
  3. External ensemble - 8/8 chips with nonzero memory via pmap + pmean on an ensemble built outside the model; an allclose check on the first and last replicas passes; steady-state 0.538s; HBM 427–624 MB/chip. No speedup was measured against a sequential eight-member run, so the experiment carries no throughput or cost claim.

Fit & rigor

  1. Empirical scaling law - R² 0.981 on 16 runs: throughput ≈ 4527.77 · chips0.963 · length−1.572. A summary of that grid, not a model of it: deviations from the measurements reach 32% at the extremes of the length range.
  1. Model pick & repeats - 0.12% coefficient of variation on steady state over three repeats (0.82% on init_params, 1.00% on the first predict); model_5's steady state took 0.403 s against 0.471 s for model_3 (14.4% less time), and model_4 took 0.472 s, the same as model_3.

Cost

Headline: idle chips cost as much as busy ones. At list prices, the default path leaves seven of eight chips idle, which makes the slice cost about the same per prediction as the T4: TPU $1.25 vs GPU $1.27 per 1,000 predictions, CPU $11.19, on the August baselines. Rented one chip at a time, the same TPU work would cost $0.157 per 1,000, about 8.1× cheaper than the GPU. Running eight independent proteins with jax.pmap on the full pod brings it to about $0.181 per 1,000.

Descriptive fit over 16 TPU runs (4 chip counts × 4 lengths), R² 0.981: throughput ≈ 4527.77 · chips^0.963 · length^−1.572. It is a summary of that grid, not a model of it: deviations from the measurements reach 32% at the extremes of the length range. On the measured grid, going from 1 to 8 chips raises cost per prediction by 22.6% at 100 residues, 7% at 250, 3% at 500 and about 1% at 1000, so the near-flat cost the exponent suggests holds only for long sequences. The external ensemble (pmap + pmean) fills all eight chips, but it has no throughput measurement and is not priced.

Next

With Google Cloud credits from Google’s TPU Builders program, we are repeating the key experiments on TPU v5e and v6e with repeated runs, adding real protein targets, testing automatic sharding with explicit annotations, and rerunning the CPU and GPU baselines on fixed Compute Engine machine types. New results will be added next to the summer 2026 numbers, not in place of them.
